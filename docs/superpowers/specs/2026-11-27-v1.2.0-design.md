# Away Mode v1.2.0: design — a no-admin Teams route

**Subject:** a second way to connect Away Mode to Teams that needs no IT or Teams admin (a Power Automate workflow sends; your own small app registration reads), chosen at install next to today's bot route, plus branded cards that say Claude Code and the project. **Out of scope:** removing the bot route, other platforms (Slack), changes to routing, approvals, commands or the recap.

## 1. Intent and why

Today a user needs a Teams admin: the Away Mode Teams app must be uploaded, and most organisations turn off custom uploads (the user's own organisation does). It also needs an Azure subscription for the Azure Bot. People without an admin can't use Away Mode at all. v1.2.0 lets them, without weakening the security invariants.

## 2. Goals, non-goals, anti-goals

**Goals**
- A user with no admin rights and no Azure subscription can install, pair and use Away Mode in Teams, with phone notifications.
- The user chooses the route at install: `workflow` (no admin) or `bot` (today's setup). Upgraders keep `bot` with no action.
- Every message in the workflow route says **Claude Code** and names the **project**, because the sender shows as "Workflows" and can't be renamed.
- Everything that works on the bot route works on the workflow route: questions, approvals (`yes|no <id>`), `#qN`, `@project`, `more`, `extend`/`until`, `snooze`, `status`, `back`, recap, doctor. `reply_routing` only if the build-phase check in section 9 passes.

**Non-goals**
- Creating the Power Automate flow automatically (the user creates it from guided steps; see 6.3).
- Changing the bot route's behaviour.

**Anti-goals** (failure even if it technically works)
- A saved sign-in that carries more than `User.Read` and `Chat.Read` by default. (The spike showed Microsoft's Graph tools app returns every permission ever granted to it in the organisation, including `Directory.ReadWrite.All`.)
- A message from someone else's flow being treated as Away Mode's own.
- The workflow URL appearing in logs, errors, doctor output, chat or files outside the keychain.

## 3. Constraints

- All CLAUDE.md rules hold: zero runtime dependencies, plain `fetch`, no inbound listener (replies by polling only, only while away), files ≤150 lines, functions ≤40, every change test-first with fakes, sender gated on the Entra object ID.
- **Scopes:** the workflow route requests exactly `User.Read Chat.Read offline_access`. The bot route keeps its three. CLAUDE.md's scope rule is updated to say "per route".
- **Another platform must be one new adapter file** (CLAUDE.md). Here it's the same platform with a different sender, so shared Graph polling moves into one module both Teams adapters use.
- Windows installer is PowerShell 5.1, CRLF. `az` CLI is already required by `create-app.ps1`.
- plugin.json changes need a version bump (lesson from 0.3.1) and every new setting goes in both `userConfig` and `mcpServers.away.env`.

## 4. Approaches considered

| | Approach | Admin? | Notifications | Verdict |
|---|---|---|---|---|
| **A (chosen)** | Workflow sends; Graph polling reads | None in most organisations | Yes | Chosen by the user. |
| B | Post into your own chat via Graph | None | **No** (no notification for your own messages) | Rejected: defeats the purpose. |
| C | Microsoft's Graph tools app only, bot kept | Yes (Teams app) | Yes | Rejected: removes only the app registration. |

**Sign-in for A**, decided by the user: default is **the user's own small app registration** (public client, `User.Read` + `Chat.Read`, created by the installer). **Fallback** is Microsoft's Graph Command Line Tools app (`14d82eec-204b-4c2f-b7e8-296a70dab67e`, authority `organizations`), only by explicit choice, for organisations where users can't register apps, with the broad-token warning in 6.6.

## 5. Spike results (2026-11-27, user's organisation, no admin)

1. Device-code sign-in with the Graph tools app: no admin prompt; token carried 20+ scopes (see anti-goals).
2. Flow "When a Teams webhook request is received" (standard, no Premium) → "Post card in a chat or channel", Post as **Flow bot**, Post in **Chat with Flow bot**, Recipient = the user, Adaptive Card = `triggerBody()?['attachments']?[0]?['content']`. POST of `{type:"message", attachments:[{contentType:"application/vnd.microsoft.card.adaptive", content: <card>}]}` → **202**. Host: `<env>.environment.api.powerplatform.com`.
3. Graph sees the card in a `oneOnOne` chat; `from.application` = `{id: "358f0194-6b0e-4dd3-af35-c24fe8a9ec87", displayName: "Workflows", applicationIdentityType: "bot"}`; `body.content` is only `<attachment id=…>`; **the card JSON is in `attachments[0].content`** (contentType `application/vnd.microsoft.card.adaptive`).
4. The user's typed reply arrives as a normal message from `from.user.id` = the user. The Workflows app then posts an automatic "I can't respond to messages" note (from the app, so ignored).
5. The Flow bot chat is shared with the user's other flows.

## 6. Design

### 6.1 Settings (plugin.json userConfig + env)

| Setting | Env | Values | Default |
|---|---|---|---|
| `teams_route` | `AWAY_TEAMS_ROUTE` | `bot` · `workflow` | `bot` (upgraders unchanged) |
| `workflow_url` | `AWAY_WORKFLOW_URL` | the flow's trigger URL, **sensitive** | — |
| `sign_in_app` | `AWAY_SIGN_IN_APP` | the user's app ID, or `graph-tools` | — |

`tenant_id` is reused (own app registration is single-tenant). With `graph-tools`, the authority is `organizations` and `tenant_id` may be empty. Bot settings are ignored on the workflow route.

### 6.2 Code shape
- `adapters/graph-chat.ts` (new): the Graph polling, `isReply`, `htmlToText`, quoted-reply lookup and bot-tag learning, moved out of `teams.ts` unchanged except that "bot message text" also reads Adaptive Card text from attachments.
- `adapters/teams.ts`: the bot route, now using `graph-chat.ts` for reading.
- `adapters/workflow.ts` (new): `send()` builds the card (6.4) and POSTs it to the workflow URL; `poll()`/`me()` from `graph-chat.ts`.
- `auth.ts`: sign-in config becomes `{authority, clientId, scopes, botSecret?}`; `botToken()` exists only with a bot secret.
- `index.ts` picks the adapter and sign-in from `teams_route`.
- `setup.ts`: pairing per route (6.5). Routing, delivery, relay, recap, commands: **unchanged**.

### 6.3 Creating the workflow (user, guided)
The `/away-mode:setup` skill and `docs/SETUP.md` give the exact steps that worked in the spike (Power Automate → Automated cloud flow → the trigger and action in section 5 item 2, Who can trigger = Anyone) and tell the user to paste the URL **into the installer prompt or `/plugin` settings, never into chat**. The Teams Workflows template list varies by tenant and isn't relied on.

### 6.4 Cards (user requirement)
Every card: a header `Claude Code · <project tag>` (bold, accent colour), a small subtle subtitle `Away Mode · <kind>` (question, approval needed, done, error, update, recap, setup), then the text (commands in monospace), then reply instructions. Messages not tied to a project use the header `Claude Code`. The same 1,200-character cap applies to the text. Sample sent and seen in the spike.
- **Install marker** *(my call, from the builder check)*: each card ends with a small subtle footer `ref <8 random chars>`, a per-install token stored in plugin data (0600). Only cards from an application whose text contains this ref count as Away Mode's own (tag learning for routing). Any flow in the organisation can post into a user's Flow bot chat, so the header alone proves nothing; those people can't read the chat, so a visible ref is as safe as a hidden one. A hidden element was rejected because the spike showed Power Automate rewrites cards (version 1.4 came back as 1.2, `$schema` dropped), so hidden elements may not survive.
- **How the adapter knows project and kind** *(my call)*: `Adapter.send(text, meta?: { project?: string; kind?: string })`. The optional argument is backwards compatible: the bot adapter and fakes ignore it; `away.ts` `announce` and the relay pass it. The text keeps its `[Claude · tag]` prefix for the bot route; the workflow adapter drops that prefix and renders the header from `meta` instead (falling back to parsing the prefix when `meta` is absent).

### 6.5 Pairing (workflow route)
1. Sign in (device code with the route's app).
2. Send a card with a one-time code through the workflow.
3. Find the chat: search the user's most recent chats for a message whose card contains the code and the install marker, from an application. Save `{route: "workflow", chatId, me}`.
4. "Paired" card. If not found within ~60 s: the flow isn't working — say which step to check (flow on? recipient right?).

### 6.6 Sign-in safety
- Doctor and setup decode the access token's `scp` claim and list it. On the Graph tools fallback, if it holds anything beyond `User.Read Chat.Read` (+ `openid profile email offline_access`), setup warns in plain words before pairing ("This sign-in can also change your directory… use your own app registration if you can"), and doctor shows ✘ with the extra permissions.
- The refresh token stays in the keychain as today.

### 6.7 Installer (`setup/install.ps1`)
- New `-Route bot|workflow`. If omitted, ask: "Do you have a Teams admin who can add the Away Mode app? (No = workflow route)".
- Workflow route: `az login --allow-no-subscriptions`; create (or reuse) a single-tenant app registration "Away Mode (<user>)" with public client flows on and delegated `User.Read` + `Chat.Read`; no secret, no Azure Bot, no Teams app. If the organisation blocks app registration, offer the Graph tools fallback with the warning from 6.6.
- Ask for the workflow URL with a hidden prompt (like the bot secret) and pass it to `claude plugin configure` over stdin.
- **Consent blocked but registration allowed** *(my call)*: this shows up at device-code sign-in in `/away-mode:setup` (AADSTS65001 / "Need admin approval"). Setup does not switch apps itself; it says in plain words that the organisation requires an admin to approve `Chat.Read`, and that if Microsoft's Graph tools app is already approved there, rerunning the installer with `-SignInApp graph-tools` may work (with the 6.6 warning). No automatic fallback.
- **macOS/Linux** *(my call)*: `create-app.sh` and `create-app.ps1` both gain a workflow mode (app registration, public client, `User.Read` + `Chat.Read`, no bot, no secret); macOS/Linux users then follow manual steps in `docs/SETUP.md`, as they do today. Only `install.ps1` is one-command.

### 6.8 Doctor
Shows the route; on the workflow route checks: URL set (never shown), sign-in scopes (6.6), chat paired, and `send_test` through the workflow.

### 6.9 Plugin manifest
Add the workflow host to `network.hosts`. Wildcard support is unknown (section 9).

## 7. Security notes
- Sender gate unchanged: only messages from `from.user.id === me` are acted on; Workflows' own notes and other flows' cards are ignored as replies.
- Spoofed cards (another flow posting "Claude Code · x") can't approve anything and, without the install marker, can't influence routing.
- The workflow URL is a bearer capability: keychain only, redacted from every error (`sig=` query), never echoed.

## 8. Testing
Fakes only (fake net for the webhook POST and Graph). Tests that must fail first include: card shape and header; marker required for tag learning; a card without the marker is ignored; URL never in thrown errors; route selection in `index.ts`; pairing finds the chat by code; scope warning for a broad token; upgrader with no `teams_route` stays on `bot`.

## 9. Open (checked live during the build, before dependent work)
1. Does a quoted reply to a Workflows card carry `messageReference` like a bot message does? If not, `reply_routing` is off on the workflow route.
2. Does `network.hosts` accept a wildcard like `*.environment.api.powerplatform.com`? If not, declare the general host and note it.
3. Does the "can't respond" note repeat after every reply? (Cosmetic; document it either way.)

## 10. Left to the builder
File split inside the 150-line limit, card element details beyond 6.4, retry/backoff for the webhook POST (reuse `http.ts`), exact wording of prompts and docs (plain English, the project's existing tone), PR split (suggested: refactor `graph-chat.ts` first, then the workflow route, then installer and docs, then release 1.2.0).

## Live results (2026-11-27)

Tried in the user's own tenant, with no admin involved:
- Install, pairing, status, an instruction, back and the recap all worked.
- The visible ref on the first cards was mistaken for a request ID. So the marker became the header element's id. A probe showed that an element id, `speak`, `fallbackText` and an invisible TextBlock all survive Power Automate and Graph, and that a custom property on the card root is stripped.
- The "I can't respond to messages" note from "Workflows" repeats after every reply.
- The wildcard host (`*.environment.api.powerplatform.com`) worked.
