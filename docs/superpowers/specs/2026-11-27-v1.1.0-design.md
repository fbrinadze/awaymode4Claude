# Away Mode v1.1.0: design

**Subject:** v1.1.0 of the Away Mode plugin. It covers several sessions away at once (routed by project) together with the lifecycle fixes from security audit run-2, five new Teams commands and checks, a README refresh, and preparation for listing in Anthropic's plugin directory.
**Out of scope:** new Microsoft permissions, any inbound network listener or card buttons, Slack or other platforms, and approving a tool "always".

Status: draft for approval · 2026-11-27 · source of truth for the v1.1.0 plan. `docs/PLAN.md` stays the source of truth for everything this document doesn't change.

## 1. Intent and why

Away Mode currently assumes one Claude Code session is away at a time, and even that assumption isn't enforced where it matters. Security audit run-2 (`~/security-audit-skill/awaymode/run-2/`) found that **every open session's Away Mode server polls the same Teams chat and shares one `state.json`**. Session ownership is checked only in the hooks. So with two sessions open, a Teams reply meant for one project can be acted on by another, and an approval can be consumed by a session that never asked for it. The user wants several sessions away at once anyway, so v1.1.0 makes the server project-aware. That fixes the bug and delivers the roadmap item in one piece of work.

The five features remove problems hit in real use: away mode ending in the middle of a meeting with no way to extend it from the phone, long commands now terminal-only (v1.0.1) with no way to read them from Teams, no way to quiet routine notes, no summary of what happened, and setup or PATH problems that each took a long time to diagnose.

The README refresh and directory listing make the plugin easier to find and trust.

## 2. Goals, non-goals, anti-goals

**Goals**
- Several projects can be away at once from one Teams chat, and every reply reaches the project it was meant for.
- People choose their routing at install time: `several` (default) or `one`, plus an optional reply-to-message switch.
- The four lifecycle requirements from run-2 (section 5.6) are met and covered by tests.
- Five Teams commands and checks ship: `extend`/`until`, `more <id>`, `snooze`, a Teams recap, and `/away-mode:doctor`.
- The README matches the code and reads plainly. The plugin passes the directory's checks and is ready for the user to submit.

**Non-goals**
- Multiple Teams chats, per-project bots, or Teams threads.
- Changing the approval rules beyond routing: `yes|no <id>`, the v1.0.1 bare-yes rules, one approval per call, and `never_relay` stay as they are.
- Submitting the directory listing. That's a user action (paid plan, Owner role); v1.1.0 makes it submittable.

**Anti-goals** (fail even if it technically works)
- Any path where a Teams message reaches a session other than the one it was meant for, or an approval reaches a session that didn't ask.
- Commands that need typing more on a phone in the common single-project case than v1.0.1 needed.
- Re-opening a v1.0.1 security fix to make routing easier.
- Hooks that become slow or import project code (they must stay under 50 ms and import nothing when away mode is off).

## 3. Constraints (from CLAUDE.md, docs/PLAN.md and the audits)

- Zero runtime dependencies; plain `fetch`; Bun runs TypeScript directly.
- No file over 150 lines and no function over 40. `plugin/server/away.ts` is already at 150 lines, so this work must split it.
- Microsoft scopes stay exactly `User.Read`, `Chat.Read`, `TeamsAppInstallation.ReadWriteSelfForUser`.
- Sender gate on the Entra object ID, before any parsing.
- Every change ships with a test that uses the fake adapter. Bug-shaped requirements get a test that fails first.
- A new user setting goes in both `plugin.json` userConfig and the `AWAY_*` env mapping.
- Every release bumps `plugin.json` `version` (v1.1.0), or `claude plugin update` won't deliver it.
- Directory validator: a command or hook path may not be built from another variable (section 8.1).

## 4. Approaches considered

| | Approach | Trade-off | Decision |
|---|---|---|---|
| A | One shared chat, routed by project: per-project state; `yes <id>` and `#qN` route by ID ownership; free text goes to the only away project, or uses an `@project` prefix | Free text needs a prefix when several projects are away | **Default** (`sessions: several`) |
| B | A, plus routing by Teams "reply to this message" | Depends on how Graph exposes quoted replies in a 1:1 bot chat; needs a live spike | **Optional switch**, off by default (`reply_routing`); ships only if the spike succeeds |
| C | One project away at a time; a new away hands over from the previous one | Simplest, but doesn't meet "several at once" | **Option** (`sessions: one`), built on A's machinery |
| | One Teams chat per project | Teams gives a user exactly one 1:1 chat per bot | Ruled out |

The user picked A as the default and asked for A, B and C to be choosable at install.

## 5. Multi-session design

### 5.1 Project identity
- Each server process knows its project directory (`CLAUDE_PROJECT_DIR`, falling back to `cwd`, as `index.ts` does today). It doesn't know the Claude Code session ID; the hooks do.
- **Project key** = the resolved absolute project path. **Project tag** (what Teams shows and what `@` matches) = the folder name, case-insensitive. If two away projects share a folder name, the tag becomes `parent/folder`. Builder's call: the exact disambiguation format.
- Claude Code started in the home folder has the tag `home`. Today that case has no project name.
- Two sessions in the **same** project share one project entry, but only one **owns** it. *(My call, from the builder check: the anti-goal forbids a verdict reaching a session that didn't ask.)*
  - Each server makes a random **instance token** at start. `set_away on` runs inside the server of the session that called it, so that server records `ownerInstance = <its token>` in the project entry. The hook records the same session's `sessionId` for the hook-side checks.
  - Each permission request reaches exactly one server, which tags it with `instance = <its token>`.
  - A later `set_away on` from the other session in the same project takes ownership and says so in Teams. Its pending items move to the new owner only if they were raised by it; any others are cancelled and listed in the recap.

### 5.2 State (schema v2)
`state.json` gets a `version: 2` field and splits into shared and per-project parts:

```
{ version: 2, me, cursor, nextQ, lease: { owner, until },
  projects: { "<project key>": {
      tag, sessionId?, awayUntil, awayStartedAt, snoozeUntil,
      questions[], permissions[], outbox[], recap[], inbox[],
      lastSentAt, lastStopAt } } }
```

- Question IDs (`q<n>`) stay globally unique through the shared `nextQ`. Permission IDs are Claude Code's own.
- **Migration:** a v1 file loads into `projects[<this server's key>]` on first load, keeping `me` and `cursor`. Pending v1 questions and permissions are dropped, with a channel note to Claude.
- **`load()` validates the shape.** Wrong types fall back to defaults field by field, and an unreadable file stays fail-closed (`me` empty). This was a run-2 hardening note.

### 5.3 One writer at a time
- Every write to `state.json`, by the server or a hook, takes a lock file (`state.lock`, created exclusively). It does read, modify, then write to a temp file with mode 0600 and rename, then unlock. A lock older than 5 seconds is considered stale and removed. This closes the run-2 lost-update gap and the hook's 0600 regression.
- The hook uses `node:fs` only (no project imports) and runs this path only when away mode is on, so it keeps its speed budget.

### 5.4 Polling: one poller, per-project inboxes
- Only the **lease holder** polls Graph. The lease is `{ owner: <project key>, until }` and is renewed each cycle; any server whose project is away may take it once it expires (`until` = now + 2 × max poll delay).
- The lease holder routes each new message (section 5.5) and appends it to the target project's `inbox`, or acts on it directly when it is global (`status`) or targets the holder's own project.
- Only the **owner instance** of a project drains that project's inbox, on its own loop (a cheap local file read with the same backoff), and does the `channel()` delivery itself.
- A permission verdict is delivered only by the server whose `instance` token raised that request. If that server is gone, the verdict isn't delivered, and Teams says "That request is no longer waiting." So a verdict can never reach a session that didn't ask.
- When the lease holder's project stops being away, it releases the lease, and another away project's server takes it on its next cycle.

### 5.5 Routing rules (in order; the sender gate comes first, unchanged)
1. `@tag …` prefix: strip it and route to that project. An unknown tag replies "No project called *tag* is away. Away now: a, b."
2. `yes|no <id>` with a live ID: route to the project holding that permission. The v1.0.1 rules apply unchanged inside that project.
3. Bare `yes`/`no`: follows the v1.0.1 bare-verdict rule **across all projects**. It counts only when exactly one permission is open across all away projects, no question is open anywhere, and the reply is newer than the permission. Otherwise it asks which one.
4. `#qN …`: route to the project that owns `qN`.
5. Commands (`status`, `back`, `extend`, `until`, `snooze`, `more`): with an `@tag` prefix (rule 1) they apply to that project only. Without one, `status` covers all projects; `back`, `extend`, `until` and `snooze` apply to **all** away projects, and the reply lists which ones; `more <id>` routes by ID.
6. Reply-to-message (only when `reply_routing` is on and the spike succeeded): a quoted reply routes to the quoted message's project.
7. Plain text: if exactly one project is away, it answers that project's newest question or becomes an instruction there, as today. If several are away and **exactly one question is open across all of them**, it answers that question. An answer can't approve anything, and this keeps typing low. *(My call, from the builder check.)* Otherwise, reply "Which project? Start with @a or @b." and deliver nothing.

Outgoing messages already start with `[Claude · <tag>]`. That stays, so every message the user sees names its project.

### 5.6 Lifecycle requirements (from run-2; each needs a test that fails first)
- **R1 Routing:** a reply reaches only its target project's session (fingerprint `lifecycle/away-state-shared-across-sessions`).
- **R2 Ownership:** a project's `sessionId` is set when its away starts (by the `set_away` PostToolUse hook for that project) and cleared when its away ends. Hooks act only for the owning session of their own project.
- **R3 No carry-over:** when a project's away **ends** (expiry, `back`, terminal input, `set_away off`), its permissions, questions and inbox are cleared and its recap is sent (section 6.4). When a project's away **starts** and no other project is away, the shared cursor jumps to now, so messages sent while nothing was away are never replayed.
- **R4 Single writer:** section 5.3.
- Also in: re-check that the project is still away between inbox items, stop an inbox batch after `back`, and use Graph `createdDateTime` (not `lastModifiedDateTime`) as the sent time for the bare-verdict comparison.

### 5.7 Hooks
The hook resolves its project key from `CLAUDE_PROJECT_DIR` or the `cwd` in its input, then reads only `projects[key]`. Its behaviours are unchanged: the AskUserQuestion redirect, the Stop note, the StopFailure outbox, and terminal input ending away. Terminal input ends away **for that project only**.

### 5.8 Settings
| userConfig | env | values | default |
|---|---|---|---|
| `sessions` | `AWAY_SESSIONS` | `several` · `one` | `several` |
| `reply_routing` | `AWAY_REPLY_ROUTING` | `on` · `off` | `off` |

`install.ps1` takes `-Sessions one` and `-ReplyRouting on`, or asks when run interactively without them. With `one`, `set_away on` in a project ends any other away project first and says so in Teams, along with its recap.

## 6. Features

Grammar: every command may start with `@tag`; matching is case-insensitive; durations use the existing `when.ts` parsing.

### 6.1 Extend from the phone
`extend 1h` / `extend 30m` adds time. `until 6pm` / `until 18:30` sets the end. The reply confirms the new end in the user's local time. If away mode already ended, the reply says so and doesn't restart it (`back` at the terminal and the `/away-mode:away` skill stay the ways to start).

### 6.2 `more <id>`: read a long command
- Permission requests keep the full redacted `input_preview` in the project's permission entry while pending.
- `more <id>` sends the full preview in parts of at most 1,000 characters, numbered "(1/3)". If more than 5 parts would be needed, it sends nothing and says it's too long for Teams.
- Previews over 600 characters (terminal-only since v1.0.1) become **approvable from Teams only after `more <id>` has sent every part**. The request is registered as "needs more", and `yes <id>` before that replies "Read it first: more <id>". This keeps the v1.0.1 rule of never approving what wasn't shown.
- `never_relay` matches stay terminal-only regardless.

### 6.3 Snooze
`snooze 30m` / `snooze until 3pm` / `unsnooze`. While snoozed, `finished` and `info` notes go into the project's recap instead of Teams. Questions, approvals and errors still come through. Snooze ends at its time or when away ends.

### 6.4 Recap in Teams
When a project's away ends, Teams gets one message: what finished (including held notes), questions left unanswered, approvals left pending (now cancelled), and what Claude parked. When away ends by terminal input, the terminal welcome-back stays as it is, and the Teams recap is sent too, marked "you're back at the terminal". Expiry is detected by the lease holder's cycle, which ends expired projects (R3) and sends their recaps.

### 6.5 `/away-mode:doctor`
A skill plus an MCP tool, `doctor`, that checks and reports one line each with a fix: the Bun version and how it's found; plugin and manifest version; tenant, bot and secret set (never printed); refresh token present; Graph `/me` reachable; bot chat found and paired; `state.json` readable, schema v2 and mode 0600; poll lease holder; away projects. Optionally it sends a test message, asking first. It must work when the server isn't connected to Teams yet, so it can explain why.

*(My call, from the builder check.)* There are two layers, because the commonest failure is the server not starting at all, and then the MCP tool doesn't exist:
- **The skill** first runs plain shell checks that need neither Bun nor the server: is `bun` on PATH (`where bun` or `command -v bun`), is the plugin installed and enabled, and is the `doctor` tool available in this session. If the tool is missing, it explains the likely causes (Bun not found, the session started without the channel flag, the plugin disabled) and stops there.
- **The `doctor` MCP tool** runs everything that needs the server: settings, tokens, Graph, pairing, state and the lease.

## 8. Directory listing preparation

### 8.1 Bun without `${user_config.bun_path}`
The directory validator blocks a command path built from another variable, which is what v1.0.1 uses. New approach:
- `plugin.json` and `hooks.json` go back to the plain command `bun`.
- `install.ps1` creates a link to Bun's real `bun.exe` in `%LOCALAPPDATA%\Microsoft\WindowsApps`, which is on every Windows user's PATH by default, so even terminals opened before Bun was installed can find it. **Spike first:** confirm that a hardlink or symlink there launches correctly from a stale terminal, and pick the link type that needs no admin rights. If the spike fails, fall back to keeping `bun_path` and accept a reviewer hold, documented in the PR.
- The `bun_path` setting is removed. Migration: the installer clears it.
- `/away-mode:doctor` reports how Bun was found.

### 8.2 Metadata and files
- `plugin/README.md` (40 words or more, links to the full README), and a `LICENSE` file (MIT) at the repo root and in `plugin/`.
- `plugin.json`: add `documentationUrl`, `supportUrl` (GitHub issues), `privacyPolicyUrl` (a new `PRIVACY.md` covering what is sent where and stored where; it must list every outbound host: login.microsoftonline.com, graph.microsoft.com, smba.trafficmanager.net), and `icon`.
- Keep the plugin folder within the directory limits: files under 256 KiB, at most 512 files, no lockfile next to a `package.json` in the plugin root.
- Pass `claude plugin validate --strict`, then the portal's Validate. The portal step is the user's.

### 8.3 Submission (user)
A checklist in the PR: paid claude.ai plan or Owner role; claude.ai/directory/manage → Submit new → Plugin bundle → the `plugin/` folder. Expect a reviewer hold, because hooks run `.ts` through Bun.
