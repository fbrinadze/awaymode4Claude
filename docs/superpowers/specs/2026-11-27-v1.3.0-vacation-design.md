# Away Mode v1.3.0: vacation mode — design

**Subject:** a vacation flavour of away mode that lasts days, keeps the PC awake, sends check-ins at times the user sets, and (pending Task 4, gated on the live spike, not in 1.3.0) keeps approvals answerable from Teams for the whole trip. **Out of scope:** automatic approvals (yes or no), running Claude Code anywhere but the user's own PC, alerting when the PC or Claude Code is down, changes to routing or the Teams routes.

## 1. Intent and why

The user wants to be away for days ("on vacation until Monday") while Claude keeps long tasks moving and checks in with them in Teams. Today away mode is built for hours: it's capped at 24 hours, approvals stop being answerable from Teams after `wait_minutes` (max 12 hours), nothing reports on a schedule, and a sleeping PC stops everything silently.

## 2. Goals, non-goals, anti-goals

**Goals**
- "I'm on vacation until Monday" (or "for 5 days") turns on vacation mode for that long, in this project, with the same Teams experience as away mode.
- Check-ins arrive in Teams at the user's `vacation_checkins` times: one summary card per away project.
- Approvals and questions stay answerable from Teams for the whole vacation (approvals: pending Task 4, gated on the live spike; not in 1.3.0); check-ins remind the user what's waiting.
- The PC doesn't sleep while vacation mode is on, and is allowed to again when it ends.
- Everything in away mode keeps working: several projects, `@project`, `extend`, `until`, `snooze`, `status`, `more`, `back`, the recap, both Teams routes (bot and workflow).

**Non-goals**
- Automatic approvals of any kind (the user chose: approvals wait for you).
- Telling the user the PC or Claude Code stopped (impossible from inside it). A missed check-in is the signal; the docs say so.
- Running on another machine or in the cloud (user chose: their own PC, left on).

**Anti-goals** (failure even if it technically works)
- Anything approved that the user didn't approve with `yes <id>`.
- A PC left unable to sleep after vacation mode ends, or after Claude Code exits.
- Check-ins so noisy that the user mutes the chat (one card per project per check-in time, no repeats if several servers run).

## 3. Constraints

- All CLAUDE.md rules hold: zero runtime dependencies (Bun built-ins like `bun:ffi` are fine), no inbound listener, files ≤150 lines, functions ≤40, test-first with fakes, sender gate on the Entra ID, scopes per route unchanged.
- Every new setting in plugin.json `userConfig` and `mcpServers.away.env`; plugin.json changes ship with the version bump to 1.3.0.
- The state store (`store.ts`) stays the single writer; new fields are validated field by field like the rest.
- Typing at the terminal ends vacation mode (it's away mode), as today.

## 4. Approaches considered

| | Approach | Verdict |
|---|---|---|
| **A (chosen)** | Vacation is a longer kind of away mode: a `vacation` flag on the project plus extras | Chosen by the user: reuses routing, multi-project, commands and the recap |
| B | A separate vacation mode with its own state and commands | Rejected: twice the surface, confusing overlap with away mode |

**Decided with the user**
- Where it runs: the user's own PC, left on (A of the hosting question).
- Approvals: wait for the user, with reminders in check-ins (option 1). No automatic no, no automatic yes.
- Check-in times: a user setting.
- Version: v1.3.0.

## 5. Design

### 5.1 Turning it on and off
- `set_away` gains `vacation: boolean` and `days: number`. Claude calls `set_away({ on: true, vacation: true, days: 5 })` or with `at`/`until` as today. Vacation has no 24-hour cap; *my call:* a 30-day ceiling, so a typo can't keep a PC awake for a year.
- The `away` skill learns vacation phrasing ("on vacation", "off until Monday", "away for a week") and asks how many days if unclear. *My call:* "until Monday" is resolved by Claude into `days` from today's date shown in the tool description, or the server accepts weekday names in `at` ("monday" = next Monday at the user's `vacation_return_time`, default 9:00). The builder picks one and tests it.
- `ProjectState` gains `vacation?: boolean` and `lastCheckinAt?: number` (validated in `store.ts`). `startAway` clears both; `endAway` clears both and releases the keep-awake.
- Everything that ends away mode ends vacation mode (time up, `back`, terminal input, `set_away off`, handover).
- `status` and the recap say "On vacation until Mon 9:00 AM" instead of "Away until".

### 5.2 Check-ins
- Setting `vacation_checkins` (`AWAY_VACATION_CHECKINS`): comma-separated local clock times, default `9:00`. Invalid entries are ignored; if none are valid, `9:00`.
- The owner server of a vacation project sends a check-in when a scheduled time has passed since `lastCheckinAt` (checked on its existing 5-second inbox timer). `lastCheckinAt` is written under the store lock first, so two servers never send the same check-in, and a server that slept sends at most one catch-up check-in, not one per missed time.
- The check-in card (kind `checkin`, subtitle "Check-in"): what finished since the last check-in, open approvals (tool, id, how long waiting, the reply line), open questions (id, text, how long waiting), parked items, and the vacation end time. Errors are sent as they happen (like finished notes), not repeated in the check-in. If nothing changed: "Still working. Nothing needs you."
- *My call:* "since the last check-in" needs recap items to carry a time: `RecapItem` gains optional `at`. Items stay in the recap until vacation ends.

### 5.3 Approvals and questions on vacation

**Status: the approval part is pending Task 4, gated on the live spike. It is not implemented in 1.3.0; today a vacation approval expires after `wait_minutes` like any other.**

- While a project is on vacation, its pending permissions don't expire after `wait_minutes` (`away.ts` `current()`/`update` cutoff and `poller.ts` `live()` skip the cutoff for vacation projects). `yes <id>` works for the whole vacation.
- Questions keep today's behaviour (after `wait_minutes`, park or safest) so long tasks keep moving; parked questions appear in every check-in until answered or vacation ends.
- `never_relay`, `more`, secrets and the sender gate are unchanged.

### 5.4 Keeping the PC awake
- While at least one project owned by this server is on vacation, the server holds a "don't sleep" request; when none is, it releases it. Released on process exit too.
- **Desktop and laptop both (user's choice C).** On a laptop the screen is kept on too, because Modern Standby laptops can drop into standby and pause programs when the screen turns off. Laptop = a battery is present (Windows `GetSystemPowerStatus` via `bun:ffi`, `BatteryFlag` ≠ 128; macOS `pmset -g batt` lists a battery; Linux `/sys/class/power_supply/BAT*` exists).
- Windows: `bun:ffi` `kernel32.SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED [| ES_DISPLAY_REQUIRED on a laptop])` on, `ES_CONTINUOUS` off.
- Lid close is a Windows power setting Away Mode can't override: on a laptop, starting vacation sends a one-line Teams note and doctor warns: "Keep the lid open, or set 'When I close the lid: Do nothing' while plugged in."
- macOS: a child `caffeinate -i [-d on a laptop] -w <server pid>`; Linux: a child `systemd-inhibit --what=sleep --why="Away Mode vacation" sleep infinity` if available, otherwise a doctor warning. Children are killed on release and die with the server.
- One module (`keepawake.ts`) with `hold()` / `release()` and a fake for tests.
- Doctor gains `✔/✘ keep awake` while on vacation.

### 5.5 Settings and installer
| Setting | Env | Default |
|---|---|---|
| `vacation_checkins` | `AWAY_VACATION_CHECKINS` | `9:00` |
| `vacation_return_time` (*my call*, only if weekday `at` is chosen in 5.1) | `AWAY_VACATION_RETURN_TIME` | `9:00` |

`install.ps1 -CheckIns "8:00,18:00"` sets the first. Settings are also editable under `/plugin`.

### 5.6 Calls from the builder check
- **Finished notes stay live** on vacation, as in away mode (a check-in doesn't repeat them; it says "3 finished since the last check-in (sent as they happened)"). `snooze` already exists for quiet; nothing is held by default. *My call:* repeating them would make the chat noisy.
- **Parked questions aren't answerable by id** after parking (today's behaviour). The check-in lists them and says "reply with what to do and it goes to Claude as an instruction". *My call:* no new dispatch path, no new security ordering.
- **Day-sized commands from Teams:** `extend 2d` and `until monday` work (days, and weekday names resolve to that day at `vacation_return_time`). The 30-day ceiling applies to them too. *My call.*
- **The 30-day ceiling applies to all away periods,** vacation or not (today an ISO `until` has no cap). Plain away doesn't keep the PC awake. *My call:* safety; no-one needs 31+ days.
- **Spike before building (gates 5.3):** confirm live that Claude Code still accepts a channel permission verdict a few hours after the request. If it doesn't, approvals can't wait for days and 5.3 goes back to the user.

## 6. Testing
Fakes only. Tests that must fail first include: vacation set for 5 days is accepted (and 31 days refused); a vacation permission is still approvable after `wait_minutes`; a non-vacation permission still expires; a check-in is sent once at 9:00, not twice by two servers, and once (not three times) after a long sleep; the check-in lists open approvals with ids; "Nothing needs you" when idle; keep-awake held while on vacation and released on `back`, expiry, terminal input and handover; status says "On vacation until"; invalid check-in times fall back to 9:00.
